# 蓝牙配网（BluFi）详细设计

> 适用范围：本设计**只在 `rv1106-mqtt-client/` 内实现**，不涉及外部参考目录。
> 协议依据：`M2 APP 蓝牙通信（BluFi）协议与指令清单.md`（V5）
> 版本：**V2（2026-09-05）** —— 架构更正：设备**无 ESP32**，BLE 由 **AIC8800** 提供，走 **BlueZ D-Bus**；设备侧需自行实现 BluFi 服务端。

---

## 1. 背景与目标

### 1.1 现状

| 项 | 状态 |
|---|---|
| 硬件 | RV1106 + **AIC8800**（Wi-Fi / BT Combo），**无 ESP32** |
| BLE 底层 | **已配置好**：APP 可发现、可连接、可通信，MTU 协商已生效 |
| Wi-Fi | 由 RV1106 本机 `wpa_supplicant` 管理，`wpa_cli` 可用 |
| 缺失 | **BluFi 应用层协议未实现** —— GATT 通路已通，但没有程序解析 APP 的 BluFi 帧、没有执行配网、没有回送结果 |
| MQTT 客户端 | 假定已联网，无网络时只能空转重连 |

### 1.2 目标

在 `rv1106-mqtt-client` 中新增 **`blufi` 工作线程**，通过 BlueZ D-Bus 暴露 BluFi GATT 服务并完成：

1. 注册 BluFi GATT 服务（Service `0xFFFF`，写特征 `0xFF01`，通知特征 `0xFF02`），广播名为 `M2-<deviceId>`；
2. 接收并解析 APP 下发的 BluFi 帧（控制帧 `0x9` 扫描请求、数据帧 `0x13` 配网数据）；
3. 调用本机 `wpa_cli` 完成热点扫描与 Wi-Fi 接入；
4. 按协议回送热点列表（`0x11`）、回执与失败通知（`0x13`）、连接状态报告（`0xF`）；
5. 配网成功后通知主流程，使 MQTT 会话可用；支持失败重试与重新配网。

### 1.3 非目标

- 不实现 BLE 协议栈与链路层（AIC8800 驱动 + BlueZ 已提供）；
- 不改动 MQTT 协议编解码与业务模块；
- 不实现 APP 侧代码。

## 2. 系统边界与角色

```
手机 APP（BlufiClient 库）
   │  BLE / GATT：Service 0xFFFF
   │     写 0xFF01（APP→设备）　通知 0xFF02（设备→APP）
   ▼
AIC8800 蓝牙控制器（BLE 模式）
   │  驱动 / BlueZ（bluetoothd）
   ▼
RV1106 用户态
   ├─ blufi 线程（本次新增）
   │     ├─ GATT 应用注册（D-Bus：org.bluez.GattApplication1）
   │     ├─ BluFi 帧编解码 + 状态机
   │     └─ wpa_cli 扫描 / 配网
   ├─ wpa_supplicant（本机 Wi-Fi）
   └─ 主线程：MQTT 会话
```

职责：

| 角色 | 职责 | 不负责 |
|---|---|---|
| BlueZ `bluetoothd` | BLE 广播、连接管理、MTU 协商、GATT 通道 | BluFi 帧内容 |
| **`blufi` 线程** | **注册 GATT 应用、BluFi 帧编解码、扫描与配网编排、结果回送** | BLE 链路层 |
| `wpa_supplicant` | 实际扫描、关联 AP、获取 IP | 蓝牙相关事务 |

> 由于 APP 侧使用 Espressif `BlufiClient`，**设备侧必须严格按 BluFi 帧格式收发**，否则 APP 无法解析。

## 3. 协议要点

### 3.1 帧格式

```
| Type (1B) | Frame Control (1B) | Sequence (1B) | Data Length (1B) | Data (N) | CheckSum (2B) |
```

- **Type**：低 2 位包类型（`0x0` 控制帧 / `0x1` 数据帧），高 6 位 Subtype。
- **Frame Control**：

| 位 | 含义 |
|---|---|---|
| `0x01` | 加密（控制帧恒为 0） |
| `0x02` | 含校验（对 `Sequence + Data Length + 明文数据` 计算） |
| `0x04` | 方向：`0` = APP→设备，`1` = 设备→APP |
| `0x08` | 要求回 ACK |
| `0x10` | 有后续分片（Data 前 2 字节为总长度） |

- **Sequence**：设备与 APP 各自维护，每帧自增 1，防重放，重连清零。
- **CheckSum**：2 字节（仅在置位 `0x02` 时存在）。

### 3.2 相关 Subtype

| 方向 | 帧 | 名称 | 数据 |
|---|---|---|---|
| APP → 设备 | 控制帧 `0x9` | Get Wi-Fi List：请求扫描 | 无 |
| APP → 设备 | 数据帧 `0x13` | Custom Data：配网信息 | `SSID:<ssid>,PWD:<pwd>[,IP:<host>,PORT:<port>]\r` |
| 设备 → APP | 数据帧 `0x11` | Wi-Fi List：热点列表 | 逐条 `长度(1B) + RSSI(1B) + SSID(N)` |
| 设备 → APP | 数据帧 `0x13` | Custom Data：回执 / 失败 | `Received SSID and password` / `Wifi connection failed` |
| 设备 → APP | 数据帧 `0xF` | Wi-Fi Connection State Report | **3 字节**：`data[0]` opmode(`0x01`=STA)、`data[1]` STA 状态(`0x0` 已连有 IP / `0x1` 断开 / `0x2` 连接中 / `0x3` 已连无 IP)、`data[2]` SoftAP 连接数(`0x00`)。依据 `BlufiClientImpl.parseWifiState()`：**少于 3 字节直接 `CODE_INVALID_DATA`**；其后剩余字节按 **(infoType, len, value) 三元组**解析，故「直接拼 SSID」也会被误读。**不带扩展字段**即 `STATUS_SUCCESS` |
| 设备 → APP | 数据帧 `0x10` | Version | `data[0]` 主版本、`data[1]` 次版本 |
| 设备 → APP | 数据帧 `0x12` | Report Error | `0x0b` = Wi-Fi 扫描错误 |
| 双向 | 控制帧 `0x0` | ACK | 被确认帧 Sequence |
| 双向 | 控制帧 `0x1` + 数据帧 `0x0` | 安全模式设置 / 密钥协商 | 见 §3.3 |

### 3.3 安全模式（关键结论）

Espressif 官方 Android API 文档中，`client.negotiateSecurity()` 是**可选的显式调用**；而 `WifiListConfig.java` 的 `connect()` 流程中**并未调用**（只有 `connect()` → `requestDeviceWifiScan()` / `postCustomData()`），`onNegotiateSecurityResult` 也仅是空实现。

**结论：本 APP 大概率使用默认模式 —— 不加密、不校验（data[0] = `0x00`）。**

实现策略（分档，按探测结果启用）：

| 档位 | 模式 | 需实现 | 状态 |
|---|---|---|---|
| L0 | 无加密无校验 | 无 | **v1 默认实现** |
| L1 | 仅 CRC16 校验 | BluFi CRC16（`Sequence + Len + 明文`） | 预留接口，按需启用 |
| L2 | AES-128 加密 | 共享密钥 + AES（IV 由 `Sequence` 派生） | 预留接口 |
| L3 | DH 协商 + AES + CRC16 | DH（1024-bit MODP）+ 上述全部 | 预留接口 |

> 设备侧收到控制帧 `0x1` 时必须**正确回 ACK 并记录模式**；若 APP 要求高于 L0，日志显式告警（v1 不解密，直接报错便于快速定位）。上线前必须抓包确认实际模式（见任务清单 P0-2）。

### 3.4 时序要求

| 约束 | 值 |
|---|---|
| APP 热点列表超时 | **10 s**，设备必须在此时间内回 `0x11` |
| APP 配置重发 | 下发成功 **2 s** 后未收到任何 `0x13` 会重发一次 → 设备侧处理须**幂等** |
| 回执冗余 | `Received SSID and password`、`Wifi connection failed` 各连发 **3 帧**，间隔 500 ms |
| APP 失败判定 | 自定义数据 `contains("failed")` 即判失败 → 回执文本不得含 `failed` |
| 分包 | 实测 MTU = **517**，ATT 层单包 payload 上限 = 517 − 3 = **514 字节**（见 §4.3.1）；但 BluFi 帧 `data_len` 为 1 字节 u8，**单帧逻辑 data ≤ 255**，超出须 BluFi 分片（每片 ≤ 255，各成一个 ATT 包） |

### 4.1 线程模型（新增 `blufi` 线程）

| 线程 | 现有/新增 | 职责 |
|---|---|---|
| `main` | 现有 | `block_on(mqtt_main)`，MQTT 会话与重连 |
| `moonraker` | 现有 | WS 客户端、状态桥 |

```

```

### 4.3 BlueZ GATT 应用注册要点

需通过 system bus 与 `org.bluez` 交互，实现以下 D-Bus 对象：

| 接口 | 说明 |
|---|---|
| `org.freedesktop.DBus.ObjectManager` | `GetManagedObjects()` 返回服务/特征树 |
| `org.bluez.GattApplication1` | 应用根对象（路径如 `/org/geeetech/blufi`） |
| `org.bluez.GattService1` | UUID `0xFFFF`，Primary = true |
| `org.bluez.GattCharacteristic1` ×2 | `0xFF01` flags `["write","write-without-response"]`；`0xFF02` flags `["notify"]` |
| `org.bluez.GattManager1.RegisterApplication` | 注册到 adapter（需先取 adapter 路径，如 `/org/bluez/hci0`） |
| `org.bluez.LEAdvertisingManager1` | 注册广播，`LocalName` = `M2-<deviceId>`（若 `bluetoothctl` 已配好可复用） |

数据收发：

- **收**：实现 `GattCharacteristic1.WriteValue(array{byte}, dict)` → 字节交给 `frame.rs` 解码；
- **发**：`0xFF02` 通过 `org.freedesktop.DBus.Properties.PropertiesChanged` 信号发送（携带 `Value`），或 `StartNotify` + `AcquireNotify`（socket 方式，性能更好但更复杂）；**v1 用 PropertiesChanged 方式**；
- BlueZ 版本需 ≥ 5.40（GATT Application API）；
- 单帧 data 上限 = **255**（`data_len` 为 1 字节 u8）；BLE ATT 层单包 payload 上限 514（见 §4.3.1）足以承载 259 字节帧，故 BluFi 分片阈值取 255 而非 514；分片由 `frame.rs` 按 255 切片。

### 4.6 模块接口规格（编码级）

> 本节为编码直接依据，函数签名以 Rust 伪代码给出；常量/字节布局与 §2、§3 协议严格一致。**编码前必读**，可消除「控制帧 0x9 到底 Type 字节是多少」「分片 2 字节总长放哪」「D-Bus 写入如何进主循环」等易错点。

#### 4.6.1 帧常量与 Type 字节换算（★易错点）

BluFi 的 **Type 字节 = `(subtype << 2) | pkg_type`**，其中 `pkg_type∈{0=控制帧,1=数据帧}`，`subtype` 即文档中「控制帧 0x9 / 数据帧 0x13」里的功能码。

> 编码时必须按此换算：文档写的「控制帧 0x9」指 subtype=0x9，实际 Type 字节 = `(0x09<<2)|0 = 0x24`；「数据帧 0x13」Type = `(0x13<<2)|1 = 0x4D`。**切勿把 subtype 直接当 Type 字节**。

```rust
pub mod ftype {
    // 控制帧 subtype（function code）
    pub const ACK: u8 = 0x00;
    pub const NEGOTIATE: u8 = 0x01;
    pub const SET_OPMODE: u8 = 0x02;
    pub const DISCONNECT_BLE: u8 = 0x08;
    pub const GET_WIFI_LIST: u8 = 0x09;
    // 数据帧 subtype
    pub const NEG_DATA: u8 = 0x00;
    pub const SSID: u8 = 0x02;
    pub const PASSWORD: u8 = 0x03;
    pub const CONNECT_STATE: u8 = 0x0F;
    pub const VERSION: u8 = 0x10;
    pub const WIFI_LIST: u8 = 0x11;
    pub const REPORT_ERROR: u8 = 0x12;
    pub const CUSTOM_DATA: u8 = 0x13;
}
pub mod fc {
    pub const ENCRYPTED: u8 = 0x01;
    pub const HAS_CHECKSUM: u8 = 0x02;
    pub const DIRECTION: u8 = 0x04; // 1=设备→APP
    pub const NEED_ACK: u8 = 0x08;
    pub const FRAGMENTED: u8 = 0x10;
}
pub const PKG_CTRL: u8 = 0x00;
pub const PKG_DATA: u8 = 0x01;

#[inline]
fn type_byte(pkg_type: u8, subtype: u8) -> u8 { (subtype << 2) | (pkg_type & 0x03) }
#[inline]
fn split_type(t: u8) -> (u8, u8) { (t & 0x03, (t >> 2) & 0x3F) } // (pkg_type, subtype)

> **设备→APP 帧的 `frame_ctrl` 约定（编码务必遵守）**：所有设备发出的帧 `frame_ctrl` 必须置 `fc::DIRECTION(0x04)`；L0 明文不置 `ENCRYPTED`/`HAS_CHECKSUM`；除"响应置位 `NEED_ACK` 的入帧"外，设备主动发出的 B1/B2/B3/B4/B5 **均不置 `NEED_ACK`**。推荐取值：
> - 普通数据帧（B1/B2/B3/B4/B5）：`fc = 0x04`
> - 分片首片（数据超 255 字节）：`fc = 0x04 | 0x10 = 0x14`（后续续片段不带 FRAGMENTED）
> - ACK 帧：`fc = 0x04`（data = `[被确认 seq]`）
```

#### 4.6.2 BluFiFrame 结构与编解码

```rust
#[derive(Debug, Clone)]
pub struct BluFiFrame {
    pub pkg_type: u8,  // PKG_CTRL | PKG_DATA
    pub subtype: u8,   // 功能码，见 ftype
    pub frame_ctrl: u8,// 见 fc
    pub sequence: u8,
    pub data: Vec<u8>,
}

impl BluFiFrame {
    pub fn decode(raw: &[u8]) -> Result<BluFiFrame, FrameError>;
    pub fn encode(&self) -> Vec<u8>; // 若 fc&HAS_CHECKSUM 则尾部追加校验（v1 L0 不启用）
    pub fn needs_ack(&self) -> bool { self.frame_ctrl & fc::NEED_ACK != 0 }
    pub fn type_byte(&self) -> u8 { type_byte(self.pkg_type, self.subtype) }
}

#[derive(Debug)]
pub enum FrameError {
    TooShort,
    BadType,
    LenMismatch { expect: usize, actual: usize },
    ChecksumMismatch { got: u16, calc: u16 },
}
```

线格式：`[type][frame_ctrl][sequence][data_len][data..][checksum:2]`，checksum 仅当 `fc & HAS_CHECKSUM`。
要点：`decode` 至少 4 字节且 `data_len` 须与后续 data 长度一致；`encode` 写入 `type=type_byte(...)`；v1 L0 不置 `HAS_CHECKSUM`，解码忽略校验字段（若存在仍按 §4.6.5 校验）。

#### 4.6.3 分片（接收重组 + 发送切片）

规则（与 §3.1 / §4.3 一致）：置位 `fc::FRAGMENTED` 时，该帧 data **首 2 字节为整段逻辑数据总长度（小端 u16）**，其后为数据片段；后续分片帧不带 FRAGMENTED、data 为续接片段；所有分片 sequence 连续递增。

```rust
pub struct FragmentAssembler {
    total: Option<usize>,
    buf: Vec<u8>,
    started: bool,
}
impl FragmentAssembler {
    pub fn new() -> Self;
    /// 喂入一帧：Some(full_data)=收齐；None=还需更多；Err=分片非法
    pub fn feed(&mut self, f: &BluFiFrame) -> Result<Option<Vec<u8>>, FrameError>;
}

/// 把一段逻辑 data 切成多帧（首片带 FRAGMENTED + 2 字节总长前缀）
pub fn split_for_tx(pkg_type: u8, subtype: u8, frame_ctrl: u8, base_seq: u8,
                    data: &[u8], max_payload: usize) -> Vec<BluFiFrame>;
```

`max_payload` = **255**（BluFi 帧 `data_len` 为 1 字节 u8，硬上限 255；BLE ATT 层单包 payload 上限 514 见 §4.3.1 足以承载 259 字节帧，故分片阈值为 255 而非 MTU−3）；首片 data = `total_len(2B) + chunk0`，故 `chunk0 ≤ 253`。**v1 固定用 255。**

#### 4.6.4 校验（v1 预留）

```rust
/// 校验字段 = Sequence + Data Length + 明文 Data，返回小端 u16（乐鑫 CRC16/CCITT；v1 L0 不启用）
pub fn checksum(seq: u8, len: u8, data: &[u8]) -> u16;
```
L1 启用时 `encode` 末尾追加该值、`decode` 校验；v1 明文不调用。

#### 4.6.5 ACK 构造

```rust
/// 构造 ACK：pkg_type=CTRL, subtype=ACK, fc 带 DIRECTION(设备→APP)，data=[被确认帧 sequence]
```

仅在收到 `needs_ack()` 的帧时回送 `data=[该帧 seq]`（链路层 ACK 由业务层在此显式处理；库不会代劳）。

#### 4.6.7 wifi：wpa_cli 封装

```rust

pub struct WifiManager {

impl WifiManager {
    pub fn new(cfg: &BluFiConfig) -> Self;
    pub fn probe(&self) -> Result<(), WifiError>;             // wpa_cli -i <iface> status 探活
    pub fn scan(&self) -> Result<Vec<ScanItem>, WifiError>;    // 触发 scan → 定时器等待 → 读 3 次 scan_results 合并
    pub fn connect(&self, ssid: &str, pwd: Option<&str>) -> Result<(), WifiError>;
    pub fn status(&self) -> Result<WifiStatus, WifiError>;
    pub fn remove_network(&self, id: u32);

pub enum WifiStatus { Disconnected, Connecting, Connected { ip: Option<String> } }
```

`scan()` 步骤：①`wpa_cli -i <iface> scan`（异步，忽略 OK）；②**定时器等待 `scan_timeout`（默认 5s）**，让 wpa_supplicant 完成一次完整扫描；③**读 3 次 `scan_results`**（每次间隔 500ms）后合并；④解析第 3 列 `signal level`→`rssi:i8`（P0-6 暂用原值），第 5 列起（含空格）→`ssid`；⑤**合并**：相同 ssid 仅保留一条，取 RSSI 更强（数值更大、更接近 0）者。三次读取在等待后补充，可累积扫描到的新热点，提升列表完整度（仍回空列表给 APP，见 §5.2）。

`connect()` 步骤：①将 ssid/pwd 持久化到 `wpa_supplicant.conf`（写入/更新单一 network 块：`update_config=1` 时 wpa_cli 亦可回写）；②比较 conf 现有内容：若该 ssid 已存在且密码一致则**不重启**，否则标记 changed；③changed 时重载 wpa_supplicant 使配置生效：优先 `wpa_cli reconfigure`（轻量重载），失败回退 `systemctl restart wpa_supplicant`；④轮询 `wpa_cli -i <iface> status` 至 `wpa_state=COMPLETED` 且 `ip_address` 存在（connect_timeout 默认 30s），否则 `Timeout`。新增/修改网络才触发重载，已连接同网络不重启（避免抖动）。

命令执行：统一 `run(args: &[&str]) -> Result<String, WifiError>`，`std::process::Command` 调用；超长命令由外层轮询超时兜底（v1 不引第三方 wait-timeout，避免依赖膨胀）。

#### 4.6.8 gatt：BlueZ D-Bus 对象与线程桥接

线程桥接（关键）：`blufi` 线程同步阻塞，D-Bus 事件循环与业务主循环需桥接。推荐：
- 用 `dbus::tree::Tree` 注册对象，`WriteValue` 实现内把字节 `write_tx.send(bytes)` 推入 channel；
- 主循环用 `mpsc::Receiver` 同时收 `cmd_rx`（主线程命令）与 `write_rx`（D-Bus 写入）；
- D-Bus 事件分发放在主循环同线程（周期性 `conn.process(Duration::from_millis(50))`）或独立子线程跑 `Connection::incoming()`，经 channel 转交主循环（参考现有 `moonraker` 线程风格）；
- `send_notify` 由主循环在回包时调用。


```
    gatt = GattApp::connect()?                 // 失败退避 1s→2s→4s…≤30s
    gatt.register(local_name)?                 // local_name = "{prefix-or-model}-{device_id}"
    event_tx.send(EnterConfigMode)
    // （可选）APP 连接建立后主动发一次 B4 版本帧：gatt.send_notify(encode_version(MAJOR, MINOR))
    write_rx = gatt.write_channel()            // D-Bus 写入经此入队
    asm = FragmentAssembler::new(); state = WaitApp; seq_out = 0
    loop:
        select { cmd_rx.recv()=>handle, write_rx.recv()=>on_app_frame(bytes) }
        // on_app_frame:
        //   f = BluFiFrame::decode(bytes)
        //   if f.needs_ack(): gatt.send_notify(make_ack(f.seq()).encode())
        //   CTRL + NEGOTIATE(0x1): 记录 f.data[0] 安全模式；若 != 0 → 日志告警(v1 不解密)；回 make_ack(f.seq())
        //   DATA + NEG_DATA(0x0):  v1 L0 忽略 payload（DH 协商后续再实现），仅按需回 ACK
        //   CTRL + GET_WIFI_LIST:
        //       state=Scanning; items=wifi.scan(); data=encode_scan_list(items)
        //       split_for_tx(DATA,WIFI_LIST,...,data,255) → send_notify 逐片(每片 data ≤255)
        //       失败 → send_notify(REPORT_ERROR 0x12, data=[0x0b])
        //   DATA + CUSTOM_DATA:
        //       prov=parse_provisioning(f.data)
        //       send_notify ×3 RECEIVED_MSG（间隔 500ms）   // B2
        //       wifi.connect(prov) → 成功 send_notify(0xF)；失败 send_notify ×3 FAILED_MSG
```
状态迁移与 §4.5 一致；失败/成功后回 `WaitApp`，配网成功发 `BlufiEvent::WifiConnected`。

## 5. 关键流程

### 5.1 初始化

```
1. 连接 system D-Bus，确认 org.bluez 存在
2. 取 adapter 路径（/org/bluez/<adapter>），确认 Powered
3. 实现 ObjectManager + GattApplication1 + GattService1(0xFFFF)
   + GattCharacteristic1(0xFF01 write) + (0xFF02 notify)
4. GattManager1.RegisterApplication
5. 注册 LE 广播，LocalName = "<prefix-or-model>-<deviceId>"，且 `ServiceUUIDs` **必须包含 `0000ffff-0000-1000-8000-00805f9b34fb`**，否则 APP 无法发现 BluFi 服务；**不可与现有 NUS demo 广播共用**（除非其广播已含 0xFFFF），应使用独立 Advertisement 对象
6. 进入 WaitApp
```

退出时：`UnregisterApplication` → 注销广播 → 断开 D-Bus。

### 5.2 扫描流程（控制帧 `0x9` → 数据帧 `0x11`）

```
收到控制帧 0x9
  1. 若请求帧置位 0x08 → 先回控制帧 0x0（ACK，data = 该帧 Sequence）
  1.5 （已关联扫描失效回退）若已关联 AP 且 scan_disconnect_fallback=true：
      wpa_cli disconnect → 等 500ms → 下述扫描（等待上限 4s）→ wpa_cli reconnect → 重起 udhcpc。
      原因：关联态扫描为空，真正常见根因是**电源/SDIO 总线不稳**（内核 sdio_err -84/-110 +
      rv1106_npor_powergood_isr voltage jitter detected）——关联后芯片高功耗把供电轨拉抖，SDIO
      传输损坏/超时，scan_results 为空；断开回到空闲低功耗态总线才稳、才能扫到。此回退只治标，
      若电源抖到连空闲扫描都失败仍返回空（日志会明指 dmesg 查 sdio_err/NPOR），需修硬件电源。
      断开支路总耗时 ≈0.5s+4s+读间隔，稳稳低于 APP 10s 列表超时。
  2. wpa_cli -i <iface> scan                     异步触发
  3. 定时器等待 scan_timeout_ms（默认 5s；断开支路用 min(该值,4000)）  让一次完整扫描完成
  4. 读 3 次 wpa_cli -i <iface> scan_results（间隔 500ms）  合并去重（同 ssid 取最强 RSSI）
  5. 解析：跳表头；取 signal level（RSSI，负 dBm）与 ssid（可能含空格，取第 5 列起全部）
  6. 编码：逐条 长度(1B)=1+len(ssid) | RSSI(1B, i8) | ssid
  7. 发送：先按 RSSI 降序排序，`encode_scan_list` 全量编码，由 `send_data` 自动按 255 字节
     分片（每片 data ≤ 255，`data_len` 不截断，首片置 `FRAGMENTED` + 2 字节总长）。
     **对端 `BlufiClient` 支持分片重组**（`parseNotification` 见 hasFrag 即累积，
     收到无 frag 的续片即拼接解析），故**不丢热点**。
     仅当对端异常（收到分片即断连）时，把 `scan_single_frame_bytes` 设为 255
     退化为单帧 + 丢弃最弱热点。
  7. 无热点也要回空列表（APP 视为「无可用热点」而非失败）
     命令失败 → 回数据帧 0x12（错误码 0x0b）
```

### 5.3 配网流程（数据帧 `0x13` → 回执 → `0xF`）

```
收到数据帧 0x13，内容为 "SSID:<ssid>,PWD:<pwd>[,IP:<host>,PORT:<port>]\r"
  1. 解析并校验（ssid 非空）
  2. 立即回数据帧 0x13 "Received SSID and password" ×3（间隔 500ms）
     **每帧 Sequence 必须递增**：`BlufiClientImpl.parseNotification()` 严格校验
     `sequence == mReadSequence.incrementAndGet()`，重复 seq 会被丢弃并导致后续帧（含 0xF）
     全部错位被弃、APP 判配网失败。最后一帧之后不再 sleep（旧实现多等 500ms）。
     —— 必须回，否则 APP 2s 后会重发；重复下发须幂等
  3. 持久化网络配置（**同 ssid 只更新密码，不新增条目**）
     优先走 `wpa_cli`：`list_networks` 找同 ssid 的 id
       · 找到且密码一致 → 仅 `enable_network`，不改动（不重载，复用现有连接）
       · 找到但密码不同 → `set_network <id> psk`（或开放网络 `key_mgmt=NONE`）更新密码
       · 未找到 → `add_network` 取 id，再 `set_network` 写 ssid/psk
       最后 `enable_network <id>` + `save_config` 写回 conf
     回退（wpa_cli 不可用，如 wpa_supplicant 未运行）：直接改写 `/data/wpa_supplicant.conf`
       · 已存在同 ssid 的 network 块 → 只替换该块（更新密码）
       · 不存在 → 追加新块；其它 network 块与全局配置一律保留
     （旧实现按行跳过 `network=`/`}` 清块，块内 `ssid=`/`psk=` 行残留且其它网络被误删，已修正）
     配置有变化才重载：优先 `wpa_cli reconfigure`；失败回退 `systemctl restart wpa_supplicant`
  4. 轮询 wpa_cli status → wpa_state=COMPLETED 且拿到 ip_address（connect_timeout_ms，默认 30s）
  5. 成功：发数据帧 0xF（仅 2 字节：opmode=0x01、STA 状态=0x0；不带 SSID/BSSID）→ 退出配网模式
     失败/超时：remove_network <id>，发 0x13 "Wifi connection failed" ×3（同 seq）→ 回 WaitApp
     全过程打印结果日志：请求（ssid / 密码位数 / ip / port，密码不打明文）、
     SUCCESS（ssid + bssid + 已回 0xF）、FAILED（ssid + 原因 + 回失败文本 ×N）
```

幂等：同一 SSID 重复到达时复用/清理临时 network，避免 `wpa_supplicant` 堆积。

### 5.4 与 MQTT 主流程协同

| 场景 | 处理 |
|---|---|
| 启动/任何时刻 | `blufi` 线程**默认常驻广播**（始终可被发现/配网），与是否联网无关；无需主线程判断网络状态。主线程 MQTT 保持 5 s 重连，联网后自然恢复 |
| 配网成功 | 发 `BlufiEvent::WifiConnected`，**主动触发 MQTT 重连 / 重新 login（立即重连，不退避 5s）**（机制见 §5.5） |
| 云端解绑 / 需重新配网 | 主线程发 `BlufiCmd::StartConfig`，`blufi` 线程重新注册广播 |
| 配网进行中 | 不阻塞 MQTT 线程，两者独立 |

> **约定变更（2026-09-17）**：v1 早期为降低侵入性，主线程对 `BlufiEvent` 仅记录日志、不改变 MQTT 行为。自「配网后重登录」需求起，改为：**配网成功即通知主线程断开当前 MQTT 会话，用新网络重新建连并 login**（详见 §5.5）。失败（`WifiFailed`）仍只记录日志，不触发重连。

### 5.5 配网成功后触发 MQTT 重连 / 重登录（新需求 2026-09-17）

**动机**：配网成功后设备切到新网络（新 IP / 路由）。若 MQTT 仍持旧 TCP 连接，可能不立即失败，出现「已联网但云端离线」。故 `wifi.connect()` 成功、拿到 IP 后，主动让 MQTT 重登录。

**机制（应用层触发，不改动 `myrtio-mqtt`）**：

- `blufi` 线程在配网成功时发 `BlufiEvent::WifiConnected`；main 事件线程收到后，经 `futures::channel::mpsc::unbounded` 通道（`reconnect_tx` / `reconnect_rx`）以 `unbounded_send(())` 非阻塞、跨线程唤醒「重连请求」。`myrtio-mqtt` 未提供 stop 接口，故用 `select` 竞速中断 `runtime.run()`。**不用 `tokio::sync::Notify`**：本项目 MQTT 主循环跑在 `futures::executor::block_on`（无 tokio runtime），而 `notify_one()` 在普通 `std::thread` 中调用，这种混用下跨线程唤醒不可靠（`notified()` 长期不返回 ready），重连不触发。改用 futures 生态的 `mpsc::unbounded` 与 `futures::block_on` 同源，跨线程 `unbounded_send` 可靠唤醒。
- `run_session` 用 `futures::future::select` 竞速 `runtime.run()` 与 `reconnect_rx.next()`，返回 `(immediate, reason)`：
  - **断网 / `runtime.run()` 出错** → `immediate=false` → `mqtt_main` **退避 5 s** 重连（避免打爆 broker）；
  - **收到信号（配网成功）** → drop `runtime.run()` future，底层 `StdTcpTransport` 的 `TcpStream` 随 `MqttRuntime` 析构关闭（旧连接即时断），返回 `immediate=true` → `mqtt_main` **立即**重连 / login（无退避）。
- `mqtt_main` 每次循环重调 `run_session`，`reconnect_rx` 以 `&mut` 传入复用，信号可多次触发；仅成功（`WifiConnected`）触发，失败（`WifiFailed`）不触发。
- **已确认**：`myrtio-mqtt`（`mqttclient/myrtio-mqtt`）的 `StdTcpTransport` 无自定义 `Drop`，`runtime.run()` future 被 drop 即关 `TcpStream`，中断方案成立。

## 6. 配置项设计

`config/mqtt-client.toml` 新增：

```toml
[blufi]
# 是否启用蓝牙配网
enabled = true
# BLE 广播名前缀（完整广播名 = "<prefix>-<deviceId>"）
# 留空则跟随 [mqtt].model；实测板子现状为 "M1S-Ge33700a6620dfddc"，与 model 默认值一致
name_prefix = ""
# BlueZ 适配器
adapter = "hci0"
# D-Bus 调用超时（毫秒）
dbus_timeout_ms = 5000
# 扫描 / 配网超时（毫秒）
scan_timeout_ms = 8000
connect_timeout_ms = 30000
# wpa_cli / wpa_supplicant 参数
wpa_iface = "wlan0"
wpa_ctrl = "/var/run/wpa_supplicant/wlan0"
wpa_conf = "/data/wpa_supplicant.conf"  # 配网后写入此文件（新增/修改网络触发重载；设备实际配置目录）
# 回执重发次数与间隔
ack_repeat = 3
ack_interval_ms = 500
# 安全模式：plain / crc16 / aes / dh_aes（v1 仅 plain）
security = "plain"
```

校验规则：

- `enabled = true` 时 `adapter` 非空；
- `scan_timeout_ms` 必须 **< 10000**（APP 列表超时），否则报错；
- 未配置 `[blufi]` 段时用默认值，向后兼容现有配置文件。

## 7. 风险与待确认项

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| ~~R1~~ | ~~现有 GATT 服务归属不明~~ | **已解除**（2026-09-05 实测）：本地 database **无 `0xFFFF` 服务**（`bluetoothctl show` 的 7 个 UUID 均为标准服务 + 厂商 NUS），`GetManagedObjects` 亦无 `GattService1` 对象 | 我们**直接注册**，无冲突。遗留：NUS demo 进程身份待查（不影响注册，但建议确认其是否会抢占广播 `LocalName`） |
| **R2** | 安全模式未最终确认 | 依据 APP 代码推断为明文，但需实测 | **P0 抓包**（P0-2）。收到控制帧 `0x1` 时打印 `data[0]`，确认档位；代码按 L0~L3 分档预留 |
| **R3** | BlueZ 版本与接口支持 | GATT Application API 需 BlueZ ≥ 5.40；`LEAdvertisingManager1` 支持度随版本变化 | 登板确认 `bluetoothd -v`；不满足则改用 `bluetoothctl` 预配广播 |
| ~~R4~~ | ~~D-Bus crate 交叉编译~~ | **已解除**（2026-09-07）：改用 `bluer`（BlueZ 官方 Rust 绑定，内部用 `dbus-rs`）；uclibc sysroot 无 `libdbus`，对交叉目标启用 `dbus` 的 `vendored` feature，由 `libdbus-sys` 从自带源码静态构建（dbus-rs 推荐的交叉编译方式） | host 构建仍用系统 `libdbus`；产物 `NEEDED` 仅 `libgcc_s.so.1`/`libc.so.0`/`ld-uClibc.so.1` |
| **R5** | RSSI 字节口径 | `wpa_cli` 输出负 dBm，`0x11` 的 RSSI 为 1 字节 | 实机抓包比对已知热点（如 `-35`）；代码预留「原值 / 绝对值」开关 |
| **R6** | 扫描超时 | APP 只等 10 s | 内部 8 s 超时；超时回空列表或 `0x12/0x0b` |
| **R7** | `wpa_cli` 权限与路径 | 需权限与正确 ctrl 路径 | 配置可调；启动探测 `wpa_cli status`，失败则禁用配网并告警 |
| **R8** | 通知吞吐 | `PropertiesChanged` 逐次发通知，热点多时较慢 | v1 可接受；若慢则改用 `AcquireNotify`（socket 写） |
